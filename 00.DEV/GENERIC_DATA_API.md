# 범용 데이터 통로 설계안

> 상태: **설계 검토 단계** (구현 전). 결정되면 이 문서를 기준으로 작업한다.

## 왜 필요한가

지금은 화면 하나마다 서버에 Controller와 Repository를 따로 만든다. 기초코드등록 화면 하나에
붙은 API 액션이 7개(`Get`/`GetMinors`/`Lookup`/`Create`/`Update`/`Delete`/`SaveMinors`)인데,
이 코드들이 실제로 하는 일은 전부 같다.

```
화면이 준 값을 받아서 -> 프로시저에 그대로 넘기고 -> 결과를 그대로 돌려준다
```

업무 로직은 전부 저장프로시저에 있고 API는 통로일 뿐인데, 그 통로를 화면 수만큼 손으로 깎고
있다. 화면이 300개가 되면 2천 개가 넘는 비슷한 메서드가 생긴다.

여기서 두 가지 문제가 나온다.

1. **화면에 검색조건 하나 추가하는 요청에도 서버 배포가 따라온다.** 배포하는 동안 그 화면과
   무관한 사용자까지 오류를 본다.
2. **새 화면을 만들 때마다 서버 코드를 써야 한다.** 화면 개발 속도가 서버 배포 주기에 묶인다.

하루에도 몇 건씩 "항목 하나 추가해달라"가 들어오는 업무 시스템에서는 이 구조가 지속되지 않는다.

## 무엇을 바꾸는가

화면별 API를 **범용 엔드포인트 2개**로 대체한다. 프로시저 이름과 파라미터를 화면이 지정하고,
서버는 권한을 확인한 뒤 그대로 실행한다.

```
POST api/data/query   조회   -> 결과셋
POST api/data/save    저장   -> ProcResult(ReturnCode/ReturnMsg/...)
```

기존 화면별 엔드포인트는 그대로 두고 새 통로를 추가한다. 한 번에 갈아엎지 않고 화면 단위로
옮길 수 있어야 한다.

### 요청 형태

```json
{
  "menuCd":   "SM_MINOR_CODE",
  "procName": "USP_SM_MINORCODE_Q",
  "params": {
    "p_work_type": "Q",
    "p_major_cd":  "CM",
    "p_major_nm":  null
  }
}
```

프로시저 호출 규약(`@p_work_type`으로 Q/Q1/N/U/D 분기, 표준 출력 파라미터)은 지금 그대로
유지한다. 바뀌는 건 "누가 파라미터 목록을 결정하는가"뿐이다.

## 보안

임의의 프로시저를 실행할 수 있게 두면 안 된다. 세 겹으로 막는다.

### 1. 메뉴 권한 — 지금과 동일

`menuCd`로 로그인 사용자의 TSMMENUAUTH를 확인한다. 지금 각 액션에 붙은
`[RequireMenuPermission("SM_MINOR_CODE", MenuAction.View)]`가 하던 일을, 요청에 담긴 menuCd를
기준으로 런타임에 한다.

| 엔드포인트 | 확인하는 권한 |
|---|---|
| query | ViewYn |
| save (`p_work_type` = N) | InsertYn |
| save (U) | UpdateYn |
| save (D) | DeleteYn |

### 2. 프로시저 화이트리스트 — 데이터로 관리

**여기가 설계의 핵심이다.** 화이트리스트를 서버 코드에 두면 "화면 추가 = 서버 배포"가 그대로
남아 아무것도 해결되지 않는다. 그래서 **TSMMENU에 컬럼을 하나 추가**한다.

```sql
ALTER TABLE TSMMENU ADD PROC_PREFIX VARCHAR(100) NULL;
-- 예: SM_MINOR_CODE -> 'USP_SM_MINORCODE_'
```

서버는 요청의 `procName`이 그 메뉴에 등록된 접두사로 시작하는지만 본다. 즉 **사용자는 자기가
권한을 가진 메뉴에 등록된 프로시저만** 실행할 수 있다.

이미 `FORM_CLASS_NM`으로 "이 메뉴가 어떤 화면 클래스를 여는가"를 DB에 두고 있으므로, "이 메뉴가
어떤 프로시저를 쓰는가"를 같은 자리에 두는 것은 자연스럽다. 화면을 추가할 때 메뉴등록 화면에서
같이 입력하면 되고 서버 코드는 건드리지 않는다.

접두사 방식이라 한 화면이 `_Q`, `_S`, `_S_1`을 다 쓰는 지금 구조가 그대로 통한다.

### 3. 파라미터 이름 제한

`p_`로 시작하는 이름만 프로시저로 전달한다. 값은 원래 SQL 텍스트가 아니라 파라미터 값이라
인젝션은 성립하지 않지만(현재 `SSP_CBO_CODE_Q`의 `where` 파라미터와 같은 원리), 표준 출력
파라미터(`@ReturnCode` 등)를 클라이언트가 덮어쓰지 못하게 하는 의미가 있다.

## 응답 형태

### query

프로시저가 결과셋을 여러 개 돌려주는 경우가 있으므로(대분류 + 소분류를 한 번에 주는 식)
결과셋 배열로 돌려준다.

```json
{ "tables": [ [ {"major_cd":"CM0001","major_nm":"단위"} ], [ ... ] ] }
```

화면은 `tables[0]`을 그리드에 그대로 바인딩한다. 지금 그리드 컬럼이 디자이너에서
`FieldName = "minor_cd"` 문자열로 잡혀 있으므로, DTO 없이 들어와도 바인딩이 그대로 된다 —
**타입 없는 결과가 오히려 지금 화면 구조와 잘 맞는다.**

### save

지금 쓰는 `ProcResult`를 그대로 돌려준다. `ReturnCode`/`ReturnMsg`/`ErrorCode`/`ErrorMsg`/
`GeneratedCode` 규약과 실패 메시지 표시 로직을 손댈 필요가 없다.

## 화면 코드는 어떻게 바뀌는가

`BaseForm`에 헬퍼를 두고 `MenuCd`는 자동으로 채운다.

```csharp
protected Task<DataTable>  QueryAsync(string procName, object parameters);
protected Task<ProcResult> SaveAsync (string procName, object parameters);
```

기초코드등록 조회는 이렇게 된다.

```csharp
public override async Task QueryClick()
{
    var keyword = txtminor_cd_q.Text.Trim();

    var result = await QueryAsync("USP_SM_MINORCODE_Q", new
    {
        p_work_type = "Q",
        p_major_cd  = keyword,
        p_major_nm  = keyword
    });

    grd1.DataSource = result;
}
```

검색조건이 하나 늘면 **익명 객체에 한 줄** 추가하고 프로시저를 고치면 끝이다.

## 변경이 발생할 때의 흐름

### A. 기존 화면에 검색조건 추가 (가장 잦은 요청)

| 순서 | 작업 | 대상 |
|---|---|---|
| 1 | 프로시저에 `@p_use_yn VARCHAR(1) = NULL` 추가 + WHERE 조건 | DB |
| 2 | 화면에 입력칸 추가, 익명 객체에 `p_use_yn = ...` 한 줄 | 화면 모듈 |
| 3 | 모듈 dll 빌드 후 `Modules\SM\`에 복사 | 배포 |
| 4 | 사용자는 그 메뉴를 다시 열기만 하면 됨 | — |

**API 무관 · 서비스 무중단.** 다른 화면을 쓰던 사용자는 아무 영향이 없다.

기본값(`= NULL`)을 주는 게 중요하다. 그래야 아직 예전 화면 dll을 들고 있는 사용자가 그 파라미터를
안 보내도 프로시저가 그대로 동작한다.

### B. 새 화면 추가

| 순서 | 작업 | 대상 |
|---|---|---|
| 1 | 프로시저 작성 (`USP_BA_ITEM_Q` / `_S`) | DB |
| 2 | 화면 프로젝트 생성 (TEMPLATE 복사) | 화면 모듈 |
| 3 | 메뉴등록에서 메뉴 + `FORM_CLASS_NM` + `PROC_PREFIX` 입력 | DB (화면에서) |
| 4 | 모듈 dll 복사 | 배포 |

**API 무관 · 서비스 무중단.** 서버 코드를 한 줄도 쓰지 않는다.

### C. 그래도 API 배포가 필요한 경우

- 인증/권한 체계 자체를 바꿀 때
- 범용 통로 자체를 개선할 때
- 프로시저로 처리할 수 없는 로직(외부 시스템 연동, 파일 처리 등)이 생길 때

드물게 일어나고, 이때만 무중단 배포(shadow copy)가 필요하다. **즉 무중단 배포는 여전히 필요하지만,
"매일 몇 건"이 아니라 "가끔"의 문제로 내려간다.**

프레임워크(BaseForm/Controls/Shared) 변경은 CoreAssembly 경로라 API 배포와 무관하다.

## 잃는 것

정직하게 적어둔다.

**타입 안정성** — 파라미터 이름 오타를 컴파일러가 못 잡는다. 실행해야 알 수 있다.
완화책: 프로시저가 "그런 파라미터 없음" 오류를 낼 때 어느 화면·어느 프로시저인지 메시지에
분명히 담고, 개발 중에는 프로시저 파라미터 목록과 대조해주는 점검 도구를 두는 방법이 있다.

**API 명세(Swagger)의 의미 축소** — 계약이 API가 아니라 프로시저로 옮겨간다. 프로시저 헤더에
파라미터 설명을 남기는 규약이 그 자리를 대신해야 한다.

**예전 방식으로 반쯤 되돌아감** — 화면이 프로시저 이름을 직접 아는 구조가 된다. 다만 클라이언트가
DB에 직접 붙던 예전 방식과는 다르다. 인증·권한·접속정보는 여전히 서버에만 있고, 실행 가능한
프로시저도 메뉴 권한으로 통제된다.

## 이행 계획

한 번에 바꾸지 않는다. 기존 엔드포인트를 지우지 않고 새 통로를 추가한 뒤 화면 단위로 옮긴다.

1. `api/data/query` · `api/data/save` 추가
2. `TSMMENU.PROC_PREFIX` 컬럼 추가 + 기존 메뉴 값 채우기
3. `BaseForm`에 `QueryAsync`/`SaveAsync` 헬퍼 추가
4. **기초코드등록 화면을 시범 전환** — 기존 방식과 결과가 같은지 확인
5. 검증되면 새 화면은 전부 범용 통로로 작성
6. 기존 화면은 손볼 일이 생길 때 함께 옮기고, 다 옮겨지면 화면별 Controller 정리

**지금 화면이 5개일 때 하는 게 가장 싸다.** 100개를 만들어 놓고 옮기면 100개를 다 손봐야 한다.

## 열려 있는 결정

- **여러 결과셋을 항상 배열로 줄지**, 단일 결과셋을 기본으로 하고 필요할 때만 배열로 줄지
- **PROC_PREFIX를 메뉴당 하나로 충분한지** — 한 화면이 다른 모듈의 조회 프로시저를 써야 하는
  경우(예: 공통 코드 조회)가 생기면 별도 테이블이 필요할 수 있다. 현재 `SSP_CBO_*` 공용 조회는
  이미 별도 통로가 있으므로 당장은 문제 없다.
- **query도 POST로 둘지** — 파라미터가 딕셔너리라 GET 쿼리스트링은 한글 인코딩과 길이에서
  불리하다. 다만 조회를 POST로 두는 것에 거부감이 있으면 GET도 검토 가능하다.
